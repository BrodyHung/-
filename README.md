# Medical Packaging Geometry Optimizer

醫療包裝幾何效率計算機。React + TypeScript + Vite，純前端、SVG 視圖、零後端。此儲存庫為可獨立部署的完整網頁專案。

## 安裝與啟動

建議 Node.js 24、pnpm 11.25.0。於本目錄執行：

```sh
pnpm install --frozen-lockfile
pnpm dev
pnpm test
pnpm build
pnpm preview
```

若電腦已裝 npm，也可以 `npm install`、`npm run dev`、`npm test`、`npm run build`；CI 以提交的 `pnpm-lock.yaml` 鎖定依賴。安裝僅允許 esbuild 的必要建置腳本。

`dev` 預設網址為 `http://127.0.0.1:5173`。正式輸出為 `dist/`，須經 HTTP 伺服器提供，不能直接雙擊來源 `index.html`。

## 操作

1. 輸入實測本體、完整平放袋材與外箱內尺寸。**所有預設值與兩個形狀按鈕都是示範值，不是太平洋醫材的官方尺寸或 CAD 校準成果。**
2. 左側可調整緩衝、安全間隙、幾何、板厚、高度、定位片與製造附加材料；每次修改即更新當前兩組配置。
3. 中央可切換整箱同尺度俯視、單格幾何與角度圖表。袋材以完整矩形顯示，本體面積另行計算。
4. 右側設定角度範圍、步長與目標後按「開始角度搜尋」。搜尋保留參數快照；更動參數後會提示重新搜尋。結果保留所有候選及失敗原因，相同目標值的角度標示並列首選。
5. 表格的「套用」會還原該次搜尋設定並套用選定角度。搜尋角度模式固定 a、s；不會一邊搜尋一邊保持指定寬或高。
6. 井字板厚、高度可獨立輸入，但與蜂巢不同時會顯示比較條件不一致。使用「同步蜂巢厚度與高度」可回到同條件比較。
7. 「儲存方案」存於 localStorage，最多 30 組；可命名、載入、刪除及選兩組比較。JSON 匯出含完整設定、當前結果、各格座標、裁片估算清單及最近搜尋快照；匯入只讀取設定並重新計算，不信任檔內結果。
8. CSV 匯出當前井字、蜂巢及最近角度搜尋結果。PNG 匯出**目前選取的 SVG 視圖**，不是整個網頁。JSON 是跨裝置備份格式；localStorage 受瀏覽器與網站來源限制。

## 幾何依據

中心線凸六角形以 a 為水平邊，s 為四條斜邊，θ 為斜邊對水平角，三角函數一律先轉弧度：

```text
u = s cos θ；v = s sin θ
W = a + 2u；H = 2v
A = H(a + u)；P = 2a + 4s
頂點 = (−a/2,−v), (a/2,−v), (a/2+u,0),
       (a/2,v), (−a/2,v), (−a/2−u,0)
```

各邊支撐線向內偏移 `t/2` 並求交點，得到紙板內部淨空；再次向內偏移 `t_cushion + c`，得到安全容納區。內縮線相交後若不能滿足全部原始半平面限制，視為空淨區。外箱邊界使用中心線向外偏移 `t/2` 的完整多邊形，包含尖端的斜接伸長，並非單純在寬高各加 t。

本體與袋材均置中，方向允許 0° / 90°。完整袋材長寬所形成的四個角必須位於安全區；對凸多邊形，這也保證全部矩形位於其中。圓形、長方形、圓角長方形的本體另以**解析支撐函數**檢查每條安全邊，圓弧取樣僅供繪圖，避免內接多邊形錯誤放行。圓角矩形的法向支撐距離為 `(w/2−r)|nx| + (h/2−r)|ny| + r`。

圓形必要高度為 `D + 2(t_cushion + c)`，但沒有以此取代完整輪廓檢查。袋材未知時不宣稱容納；袋材周長 `2(L+W)` 只是平面矩形近似。啟用周長候選且輸入 P > 0 時，以 `s=(P−2a)/4` 產生候選，再重新執行輪廓檢查。P = 0 時使用 2(L+W) 的平面周長估算；兩者都不可用時保留手動 s。

手動延伸不會縮短袋子：有效袋長 `max(L_bag, D + 2 × 單側延伸)`。自動模式的延伸為 `max(0,(L_bag−D)/2)`。圓角本體的實際半徑自動限制於短邊一半。

## 規則排列搜尋

不是單格面積相除。每個放入單元都有實際頂點座標，使用凸多邊形 SAT 分離軸定理檢查碰撞，邊界接觸允許、內部正面積重疊拒絕。非共用壁使用外擴板材輪廓檢查相互碰撞；共用壁使用中心線多邊形，接觸邊由材料聯集去重。

- 井字：中心線格寬 = 內長 + t、格高 = 內寬 + t。有限水平 / 垂直內隔板數決定最多行列數；外圈封閉隔板也計入材料。另搜尋整體旋轉及包裝旋轉。
- 蜂巢：搜尋一般對稱六角形的共邊格點：列中心距 `a+u`、同行縱距 `2v`、奇偶列縱向錯位 `v`，另搜尋外包矩形直列與使用者指定錯位比例的規則族。共邊格點旋轉時同步旋轉整個格點。非共用模式使用分離格點，雙壁材料不去重。
- 逐格檢查外擴板材是否位於箱壁間隙內，不放入超界格。不同規則與整體旋轉均比較最大件數，同件數時選較少總板材的規則。**同角度只保留該規則搜尋所得最大裝載配置**，不是對所有任意件數與排列做多目標窮舉。
- 定位片每層左右交替排列。保守預留左右各一條「定位片長度」的完整側帶，寬度沿箱寬排列，過長時拒絕。定位片占地與展開材料均計入；即使單側只有一片，仍預留兩側，可能低估可裝載數量。
- 每軸最多 40 格、角度最多 251 組，避免瀏覽器無界運算。未搜尋任意平移相位、自由旋轉、混合方向、任意多邊形拼排或局部非規則排列。這是**規則排列搜尋結果，不是全域最佳解**。

## 材料模型

同一直線的邊段以方向與法向位置分組，再將投影區間求聯集，因此完整及局部共用邊都只計一次。浮點容差為 1e−6 mm 等級，直線分組四捨五入到 5 位小數。非共用模式保留每片獨立邊。

| 類別 | 定義 |
| --- | --- |
| 理論隔板材料 mm² | 有效中心線總長 × 隔板高 × 層數 |
| 裁切展開面積 mm² | 理論材料 + 每格卡榫加工預留 + 每層折返 + 定位片面積，依層數加總 |
| 含損耗總板材 mm² | 裁切展開面積 × (1 + 製造損耗率/100) |

井字橫縱隔板由共線連續段估算裁片；每個連續中心線段以「段長 × 高度」記錄於 JSON 的 `pieces`，數量欄位為層數。蜂巢亦輸出直段材料清單。這是**製造前展開估算**，尚未決定折彎成哪條連續長板、接頭搭接、折彎補償、實際刀縫、裁切扣槽、紙板紋向、庫存大板規格與排版餘料。使用者可在加工預留、折返與損耗率輸入製造額外用量，不能把估算清單當成完成驗證的刀模。

## 指標與最佳化

- 裝載密度 = 總件數 / 箱內體積，畫面換算 件/L（1 L = 1,000,000 mm³）。
- 裝載提升率 = `(蜂巢件數 / 井字件數 − 1) × 100%`。
- 總紙板減量率 = `(1 − 蜂巢含損耗面積 / 井字含損耗面積) × 100%`。
- 每件紙板 = 含損耗總面積 / 總件數；每件減量率以同樣比值公式計算。正值表示減量，負值表示增加；分母為零或每件量不可定義時顯示「—」。
- 空間利用率分別以「單層所有本體面積 / 箱底面積」及「單一本體面積 / 單格紙板內部淨面積」計算，不把袋材或隔間面積冒充本體占用面積。
- 本體圓面積 πD²/4；圓角矩形面積 D×寬 − (4−π)r²。
- 三種角度目標：最大件數、最小每件含損耗紙板、最小排列包絡體積。包絡體積包含定位片、外側板材與堆疊高度；不會改變輸入外箱。
- **固定外箱本身體積對所有角度都相同**，因此第三目標明確採「排列包絡體積」作為可比較的占用體積。未固定需求件數，可能偏好較少裝載方案，應同時查閱件數；不是反求可承運的最小外箱。
- 多角度目標值在 1e−6 容差內相同時列為並列，不使用材料或角度暗中破除目標平手。表格保留所有無解候選。搜尋結果以按鈕啟動時的快照為準。

## 三維與實務限制

俯視本體形狀簡化且置中，袋材採完整平放矩形。這是保守的二維幾何模型，沒有實測已封裝袋子的厚度、皺折、封口形狀或可容許變形輪廓；需要實品輪廓才能改用更貼近實物的模型。

層高 = `max(隔板高, T + 2(t_cushion+c))`。開啟多層時，層數為 `floor((箱高−2箱壁間隙)/層高)`；關閉時最多一層。未加入層間承重整片、上下蓋、封箱材料與實際外箱紙板。定位片連接、卡榫強度、壁板厚度的節點製造可行性，均須回 CAD 與樣品驗證。

沒有有限元素分析、跌落、運輸衝擊、承重、紙材吸濕、滅菌屏障摩擦與法規合規驗證。工具不對臨床使用安全作結論。

## GitHub Pages

部署目標：BrodyHung/-，主分支 main，工作流程 .github/workflows/pages.yml。部署是否成功請以 Actions 最新執行結果為準。

1. 將完整專案提交到 GitHub 儲存庫根目錄。
2. 工作流程位於 `.github/workflows/pages.yml`，建置輸出路徑為 `dist`。
3. 在儲存庫 Settings → Pages 選擇 GitHub Actions 作為來源。
4. 推送到 `main` 或手動執行工作流程；其他主分支請同步修改 branches。PR 只測試建置，不部署。
5. 工作流程安裝鎖定依賴、跑測試、建置並部署 `dist` 至 Pages，完成後查看部署回傳網址。

Vite 使用 `base: './'`，支援 GitHub Pages 儲存庫子路徑。無前端路由，不需 404 重導。應用不需 API key、外部服務或資料庫。若同一儲存庫已有另一套 Pages 部署，應選擇其中一個工作流程，避免彼此覆蓋。
